# 02 架构

## 1. 四层技术栈

| 层 | 组件 | 职责 |
|---|---|---|
| 在线服务 | TypeScript / Node | S0–S3 四级短路、query 日志、打标队列 |
| 判定与融合 | BGE-M3 dense(1024) · bge-reranker-v2-m3 · RRF | 宽召回、三分类判定、多路融合；模型本地常驻 |
| 存储 | PostgreSQL 16+ · pgvector · pg_trgm(GIN) · B-tree | 中文译义、别名、embedding、日志、打标同库同事务 |
| 离线生产 | Python | 变体批量生成（仅短语/句子）、embedding 刷新、人工核验、golden set 评测 |

在线与离线边界按语言划分，与用户既定技术栈一致：产品/服务侧 TS，LLM 与数据处理侧 Python。

## 2. 在线链路 S0–S3

| 层 | 处理 | 短路条件 | 成本 |
|---|---|---|---|
| S0 | 中文 query 直接精确匹配 `canonical_zh` 或已核验别名 | **精确相等**（允许去标点、空格、语气词的轻量归一化）且歧义检测通过 | 纯 B-tree，零 LLM / 零向量 / 零 reranker |
| S1 | 轻量中文形态归一化：叠词（狗狗）、时态助词、儿化、同义替换表 → 回查 | 归一化后精确命中 | 零 LLM |
| S2 | 变体表命中（共识规范译法 / 口语变体 / 直译变体 / 词典义项） | 命中且无歧义 | 零 LLM |
| S3 | LLM 表达归一化 → 宽召回 → reranker 三分类 | 长尾兜底 | 1 次 LLM + 向量 + reranker |

**动态准入（必须遵守）**：S0 的准入条件与条目类型无关，只看「是否精确命中」与「歧义检测是否无冲突」。用户说明单词「大多是直译」，意味着存在非直译单词；短语与句子里也有直译条目。按 `corpus_type` 写死分支会造成两侧边界漏判。`corpus_type` 只用于离线决定生成多少个别名和 golden set 分层。

**类型化检索策略**（离线与索引层，非在线路由）：

| 类型 | 中文长度 | 主索引 | 辅助 | 说明 |
|---|---|---|---|---|
| 单词 | 1–4 字 | B-tree 精确匹配 + 词典义项 | 向量仅做联想扩展 | `pg_trgm` 在超短中文串上靠 padding 才能凑出 trigram，区分度差；且 query 与译义绝大多数精确相等，上模糊是负优化 |
| 短语 | 3–12 字 | `pg_trgm` (GIN) | 中文向量，RRF 融合 | 中等长度，两者都有效 |
| 句子 | 8–30 字 | 中文向量 | trigram 辅助 | 措辞与语序变体发散，枚举不经济 |

统一策略会强迫在 1 字单词与 30 字句子之间取一个折中阈值，而词级与句级相似度分数分布不在同一量级，必然系统性误判。

## 3. L2 判定与三分类

S3 的宽召回阶段：`pg_trgm` + 中文向量经 RRF 融合，**不设硬阈值**（阈值只用于截断候选数 K，不用于判定命中）。

判定由 `bge-reranker-v2-m3` 完成，doc 侧拼接「中文翻译 ‖ English」，让 cross-encoder 同时看到两侧：只喂中文未必抓得住 `不要算我` 与 `算我一个` 的极性差异；只喂英文则退化为跨语言重排、质量下降。

| 判定 | 系统行为 | 是否打标 | 识别依据 |
|---|---|---|---|
| 精确对应 | 主路径返回 | 否 | verifier 判定 |
| 并列精确对应 | **全部返回** | 否 | 词典义项 / 变体表中已显式登记且 `verified = true` |
| 联想相关 | 主路径返回 | **是** | 近义但未登记 |
| 不相关 | 不返回 | **是** | verifier 判定 |

**判定权在 verifier，不在相似度分数。** reranker 的价值在判定而不在排序：cosine 排序本身够用，但「联想相关 / 不相关」的边界需要 query-doc 联合编码才能给出。

**并列精确对应与译法歧义的区分**（见 `03-data-model.md`）：同一中文说法指向多条英文时，若这些关系全部已登记且已核验，属并列精确对应，全部返回不打标；若存在未核验、来源冲突或关系类型不明，属译法歧义，禁止 S0 短路、强制走 L2 并打标。区分依据是数据状态，不依赖模型置信度。

## 4. 打标队列

| 类型 | 含义 | 人工动作 |
|---|---|---|
| `missing_corpus` | 英文库里没有该条目 | 补语料 |
| `translation_fix` | 中文翻译不准 | 修正译法（对接既有核验工作流） |
| `missing_alias` | 缺表达变体别名 | 补别名，可 LLM 预填 + 人工校对 |
| `translation_ambiguity` | 同一中文说法对应多条英文，登记关系不可信 | 明确关系并置 `verified` |

附加标志位 `low_confidence`：返回了结果但判定置信度低，优先级最高。

队列按 query 频次排序决定人工投入顺序。S3 产出的归一化表达与判定结果回填 S2 变体表，回填行带 `source = llm_batch` 且默认 `verified = false`，**不得覆盖 `verified = true` 的人工结果**。

## 5. 离线生产

- **范围**：仅 5,000 条短语/句子需要 LLM 生成变体（8–12 个/条）。10,000 个单词的译义直接从权威词典导入，不调用 LLM。
- **规模**：离线调用约 5,000 次（可 batch 多条/次），一次性成本；变体表约 6–9 万行，其中 2–3 万行来自词典导入。
- **产物**：别名行、embedding 向量、`golden_case` 评测结果、歧义登记。
- **闭环**：人工核验通过 → 置 `verified = true` → 同事务刷新该条 embedding → 下次同类 query 走 S0/S2。

## 6. 实现时必须保持的不变量

1. 命中判定权只在 L2 verifier；任何相似度分数都不得直接判定「命中」。
2. S0 只允许精确相等短路，不允许 `similarity ≥ 阈值` 短路。
3. 联想相关一定打标；并列精确对应一定不打标。
4. LLM 回填不覆盖 `verified = true` 的别名与人工修正的中文翻译。
5. 在线路由不按 `corpus_type` 分支。
6. 中文别名与英文条目是多对多；同一 `zh_text` 允许指向多个 `entry_id`。
7. 人工修正中文翻译后，embedding 重刷在同一事务内完成。

## 7. 为什么不用备选架构

| 备选 | 否决理由 |
|---|---|
| 纯跨语言向量检索 | ANN 永远返回 top-k，没有「未命中」状态，与打标需求结构性冲突；词级与句级分数分布不同量级，全局阈值不可靠 |
| 在线翻译 + 英文全文检索 | 意译 case 中英字面零交集（`我明白了` / `I see`），翻译路径会全军覆没；且延迟、成本、可复现性差 |
| 判定与扩展分离（扩展折叠展示） | 用户明确要求口语变体与联想扩展在主路径 |
| 进程内 numpy 向量矩阵 | 需自维护多实例同步、模型升级全量重刷、与 PG 的事务一致性；一人团队维护成本超过收益 |
