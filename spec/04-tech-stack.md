# 04 技术选型

## 1. 选型清单

| 层 | 选型 | 未选的替代 | 不选理由 |
|---|---|---|---|
| 存储 | PostgreSQL 16+ 单库 | — | 中文译义、别名、embedding、日志、打标同库同事务 |
| 精确索引 | B-tree（`canonical_zh`、`alias.zh_text`） | Hash | 支持前缀查询，运维无差异 |
| 模糊索引 | `pg_trgm` + GIN | Elasticsearch + IK 中文分词 | 15,000 条中文短文本，分词收益不抵一个 JVM 组件的维护成本；对 1–4 字单词几乎无效 |
| 向量 | **pgvector，精确暴力扫描，不建 HNSW** | Qdrant / Milvus / 进程内 numpy | 15,000 × 1024 ≈ 61 MB，暴力几十毫秒；独立向量库引入一致性问题；进程内矩阵需自维护多实例同步与模型升级重刷 |
| Embedding | **BGE-M3** dense 1024 维（中文侧） | text-embedding-3-large / bge-large-zh | 中文检索开源事实标准，可本地部署无 API 依赖，与 reranker 同生态 |
| Reranker | **bge-reranker-v2-m3**（本地常驻） | LLM verifier | 描述式 query 已排除，cross-encoder 足够；边际成本是延迟不是钱 |
| 多路融合 | RRF | 加权求和 | 单词/短语/句子分数尺度不同，RRF 免调权重 |
| L0 归一化 | 结构化 LLM API + 规则前置 | 本地小模型 | 仅 S3 长尾触发，一阶段不上本地部署 |
| 在线服务 | TypeScript / Node | — | 与既定前端栈一致 |
| 离线 pipeline | Python（变体生成、embedding 刷新、评测） | — | 与既定 LLM/agent 栈一致 |

组件全部取各自领域社区最大、最成熟的方案；不引入任何未经验证的冷门扩展（如中文分词用的 zhparser / pgroonga）。

## 2. 关键判断的底层理由

- **不建 HNSW**：15,000 条精确扫描足够。建 ANN 索引会引入近似漏召回，而本方案的最小对立对（`count me in` / `count me out`）对漏召回特别敏感；同时省掉索引维护。
- **reranker 不是可选项**：它的价值在**判定**不在排序。cosine 排序本身够用，但「联想相关 / 不相关」的边界以及是否触发打标，需要 query-doc 联合编码才能给出。
- **doc 侧拼接中英双字段**：只喂中文，cross-encoder 未必抓得住极性差异；只喂英文，中文 query 对英文短句退化为跨语言重排、短句质量下降。拼接后成本不变，`bge-reranker-v2-m3` 本身是多语言模型。
- **PG 单库而非独立向量库**：人工修正中文翻译后，重刷单条 embedding 与更新索引可在同一事务完成；独立组件会把这个闭环变成分布式一致性问题。

## 3. 工程参数

| 参数 | 值 | 依据 |
|---|---|---|
| embedding 矩阵 | 15,000 × 1024 × 4 B ≈ **61 MB** | `vector(1024)` 单表即可 |
| 变体表规模 | 约 **6–9 万行** | 词典导入 2–3 万 + 短语/句子 8–12 个/条 |
| 离线 LLM 调用 | 约 **5,000 次**（仅短语/句子，可 batch） | 单词译义从词典直接导入，不生成；较全量生成降约 67% |
| 离线 token 量级 | 数百万，一次性 | 每条生成 8–12 个中文变体 |
| S3 单次 LLM | T_in ≈ 150–200 token，T_out ≈ 30–80 token | 描述式排除后 prompt 收窄为结构化改写 |
| 主流量路径 | 10,000 单词走 B-tree 精确匹配 | 零 LLM / 零向量 / 零 reranker |

## 4. 成本模型

```
日成本 = Q × r × (P_in × T_in + P_out × T_out)
Q = 日 query 量，r = 落到 S3 的占比
```

- **只有 L0 的 token 消耗随 query 量线性增长**，是主要变量。
- `bge-reranker-v2-m3` 是本地常驻模型，固定成本 + 边际延迟，**不产生按次计费项**；向量召回与 15,000 条精确余弦同为本地算力。三者不能笼统相加成「成本翻倍」。
- `r` 只能由线上 `query_log.s_level_hit` 统计，**不能由人工构造的 golden set 推算**（评测集刻意均衡，不代表真实分布）。
- 降本路径：S1 规则归一化 + S2 变体表覆盖提高 → 更多 query 在 S0/S2 短路；S3 结果回填 S2，使同类 query 下次不再触发 LLM。

**缓存的局限**：缓存优化掉的恰恰是不需要优化的部分。直译词高频集中、命中率高，但本就该走精确索引；口语变体措辞发散、天然长尾，正是必须过 LLM 的部分，缓存命中率最低。因此缓存不能替代离线变体表。

## 5. 延迟模型

| 路径 | 典型延迟 | 说明 |
|---|---|---|
| S0 / S1 / S2 | 毫秒级 | 纯 PG 索引查询 |
| S3 完整通道 | 约 0.5–2 s（估算，非实测） | LLM 生成占九成以上；reranker 与向量召回合计几十至几百毫秒 |

同步延迟已由需求侧允许。快速通道覆盖大部分流量，体验差异比总成本更关键。S3 可异步执行向量扩展，主结果先返回；embedding 服务不可用时主链路不受影响。

## 6. 部署形态

- 单机 PostgreSQL，模型（BGE-M3、reranker）本地常驻，无外部 API 强依赖（L0 归一化除外）。
- 离线 pipeline 一次性运行 + 人工核验后增量重跑；模型升级时全量重刷 15,000 条 embedding，按批次事务执行。
- 不引入消息队列、缓存中间件或独立检索服务。
